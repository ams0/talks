Common words survive whole. ETL splits. deserialization splits. A token is a byte sequence the tokenizer saw often enough to keep.

60 seconds. Walk the amber chips.

"This is the answer the model is going to give you, taken apart. Fifty-four characters. Nine words. Twelve tokens — so it is neither. Look at the amber ones: E-T-L is two tokens, because the tokenizer has never seen enough ETL to keep it whole. Deserialization is two. But 'failed' and 'nightly' survive intact, because they are common. A token is just a byte sequence that showed up often enough in the training corpus to be worth an entry."

Real splits from tiktoken, o200k_base. Say that — people assume these diagrams are drawn by hand.

If someone asks why there's a leading space on most chips: the space is part of the token. That is why "ETL" mid-sentence and "ETL" at the start are different tokens.

Because the two obvious answers are worse.

Letters: nothing to learn, enormous sequences. Words: short sequences, and agentgateway isn't in the dictionary. Subwords are the trade.

55 seconds. Left, right, middle — in that order.

"Why not just use letters? Because your vocabulary is two hundred and fifty-six and every sentence becomes enormous — and attention cost grows with the square of sequence length, so that is ruinous. Why not whole words? Because the vocabulary is unbounded. New words arrive every day — agentgateway, llm-d, your internal service names — and a word-level model simply cannot represent them. Subwords are the compromise: a fixed vocabulary that can still spell anything it has never seen."

If challenged on "256": byte-level, so 256 is exactly right — not an alphabet, the byte range. That is also why these models can handle any script on earth without a special case.

byte-pair encoding

The vocabulary is learned, not written.

Start from bytes. Merge the most frequent pair. Repeat 200,019 times. GPU earned its own entry; Kubernetes did not.

65 seconds. The last line is the one that lands.

"Nobody sat down and wrote this vocabulary. You start from raw bytes, you count which pair occurs together most often, you merge it into a new symbol, and you do that two hundred thousand times. What falls out is a frequency ranking of the internet. GPU appears often enough to earn a single entry. Kubernetes — the thing we are all running — does not; it costs you a K and then everything else. And agentgateway is free, but only because 'agent' and 'gateway' were already common separately."

Then land it: nothing in this vocabulary understands anything. It is compression, fitted to a corpus. Every semantic thing the model does happens after this point, in the weights — not here.

This is also the honest setup for the next slide: if the corpus was mostly English, the compression is tuned for English.

02

Where the agent stops being trusted

stop 03 · the gateway

8 seconds. This is the act you said you'd spend time on — signal it.

Three languages. One is about tokens.

70 seconds. Start of the gateway act. Slow down.

"Here is the thing most LLM gateways get wrong. They sit in front of chat completions and call it done. But an agent does not mostly talk to a model — it talks to tools, over MCP, and to other agents, over A2A. And a completion writes you a bad paragraph. A tool call drops a table. The dangerous traffic is the middle lane, and almost nobody has a policy enforcement point in front of it."

agentgateway handles all three in one data plane: Rust, one binary, donated by Solo.io to the Linux Foundation's Agentic AI Foundation. Envoy AI Gateway and kgateway are fine alternatives — the argument is the shape, not the vendor.

agentgateway · the control that did not exist a year ago

Per tool. Not per service.

75 seconds. This is the slide the gateway act exists for.

"This is the control that did not exist a year ago. Not 'may this agent use MCP' — but 'may this agent call delete_customer, given these claims, in this environment'. Written in CEL, evaluated in the data plane, on every single call. Your agent is a program that writes its own next action. You would not give a junior engineer unrestricted production credentials on day one, and you should not give it to something that hallucinates."

If asked how tools get discovered: the gateway can federate several MCP servers behind one endpoint and filter the tool list it advertises — so the agent never even learns that delete_customer exists. That is better than denying it at call time.

agentgateway · identity

It acts as somebody.

55 seconds.

"The single most common thing I see in production agent stacks is a long-lived API key in an environment variable, shared by every user of the agent. Which means your audit log says 'the agent did it'. Useless. What you want is the human's identity carried through the agent, verified at the gateway, exchanged into a short-lived credential, and presented to the tool — so the log says who, not just what."

JWT, OIDC, OAuth token exchange, SPIFFE workload identities. All standard, all boring, none of it specific to AI — which is the reassuring part.

03

Which GPU answers

stop 04 · route

8 seconds.

Identical. Not interchangeable.

The fix is an InferencePool where the Service was. Your application team changes nothing.

85 seconds. The biggest money slide of the first half.

"Three replicas. Same image, same weights, same answer. And one of them already has thirty thousand of your thirty-one thousand tokens sitting in its KV cache, because this is turn seven of a conversation. That replica is seventy times cheaper for this specific request. A Service cannot know that. It round-robins, you land on a cold replica, and you pay for the same prefill twice. No error. No 503. The dashboard is green."

A Service balances connections. An InferencePool balances requests. The signals are vLLM's own Prometheus metrics — nothing proprietary. Gateway API Inference Extension, v1.6, five gateways implement it.

If challenged: yes, this is also why connection-count load balancing fails — one streaming SSE connection can hold for ninety seconds using a sliver of a GPU while another saturates it.

95 seconds. The heart of the talk. Let the two indigo bars do the work.

"Look at the bottom bars. They are the same. Seventy-one gigabytes of weights, read out of memory, in both cases. Now look at the top bars. On the left, four and a half petaflops of arithmetic. On the right — that sliver — a hundred and forty-one gigaflops. Thirty-one thousand times less work, for exactly the same memory traffic. Prefill uses the GPU as designed. Decode turns the most expensive accelerator NVIDIA sells into a very fancy memcpy."

If someone wants the ratio: prefill runs at ~62,000 FLOP per byte read, decode at 2. The card breaks even around 1,250. One is fifty times over, the other six hundred times under.

Every operational consequence follows from this slide: why your latency dashboard needs two numbers, why a bigger GPU did not help, why there is a whole project devoted to running these on separate machines.

"Same eight point nine milliseconds. Sixty-four tokens instead of one. The cost per pass does not move; the cost per token collapses. This is why throughput and latency are different products, why inference is a utilisation game, and why everything in the next three slides exists."

llm-d · prefill/decode disaggregation

Stop making them share.

Two deployments, two sets of knobs, one pool in front. Earn this — do not start here.

70 seconds.

"Once you accept that prefill and decode are different machines, the conclusion is obvious: stop making them share a GPU. Prefill pods sized for raw compute, with almost no KV cache. Decode pods sized for memory bandwidth and capacity, with an enormous one. The KV cache travels between them over RDMA. llm-d reports up to seventy percent more tokens per second — and a significantly more complicated cluster."

Be honest: this is the right answer at scale and the wrong answer for almost everyone in this room. Cache-aware scheduling — the green box on the left — is where the money is and where the risk is not.

On one GPU, the cheap version of this is chunked prefill, which slices a long prefill and interleaves it with everyone else's decode steps. It is on by default in vLLM. Most of you already have it.

"llm-d is not a new engine — it is vLLM plus the three problems you only get when you have a fleet. Which replica should answer. Should prefill and decode live on the same box. "Cache hits survive a pod restart" is the line — that is the difference between a cache and a coincidence.

05

Inside the engine

stop 06 · vLLM

8 seconds.

continuous batching

No queue. A scheduler.

The batch is torn down and rebuilt every forward pass — roughly a hundred times a second.

60 seconds. Point at the hatching, then at the teal.

"Your request does not wait its turn and then get served. It joins a batch that is rebuilt on every single forward pass, next to total strangers. On the left, the old way: four requests start together, and because the batch leaves together, three of them sit there computing padding. On the right, the moment a sequence emits its stop token the slot is free, and the scheduler admits someone else on the very next pass."

The consequence worth saying out loud for the SREs: your tail latency is a property of your neighbours. "It was fast in staging" is not evidence of anything.

Admission is a memory decision — do I have free KV blocks — not a queue position.

The KV cache gets a page table.

Before

Reserve for the longest thing that might happen.

20–40% utilisation. The rest is fragmentation you paid for.

PagedAttention

Blocks of 16 tokens, scattered, with a page table.

Near-zero waste. Shared prefixes point at the same physical blocks.

55 seconds.

"vLLM's founding idea was to steal the oldest trick in the operating system. Stop reserving a contiguous slab for the longest answer a sequence might produce, and start handing out sixteen-token pages with a block table. Utilisation goes from a third to over ninety percent. And sharing falls out for free — two sequences with the same prefix just point at the same physical blocks."

prefix caching · on by default

Turn seven. You pay for one block.

60 seconds. This is where the two halves of the talk meet.

"Blocks are keyed by a hash of their contents and everything before them. Your system prompt, your tool schemas, your project instructions — byte-identical on every turn. So on turn seven, the prefill you actually pay for is the delta. Nine hundred milliseconds becomes twelve. But — and this is the whole argument — only if the router sent you to the replica that is holding those blocks. Cache-aware serving and cache-aware routing are the same optimisation in two different projects, and one without the other buys you nothing."

Free gift for the room: a timestamp or session ID at the top of a system prompt invalidates every block after it and silently destroys your hit rate. Put volatile content at the end.

75 seconds. Reveal one bar per click.

"Weights are rent — you pay it once per replica whether anyone is talking to the model or not. The KV cache is the inventory you actually sell: every token in flight lives there. So the interesting effect of quantisation is not a smaller download. It is that the same card went from eleven concurrent agent conversations to thirty-five. Two flags. No new hardware."

Numbers if challenged: Llama 70B keeps 320 KB of KV per token at BF16, 160 KB at FP8. --gpu-memory-utilization 0.9 leaves 259 GB of the 288. Sessions counted at the 31,219-token context from act one.

And the diagnosis: if gpu_cache_usage_perc is pinned at 1.0 you are out of concurrency, not compute. A faster GPU will not help. This slide will.

Why read all of it?

Dense

Every parameter, every token.

64 of 64 read
71 GB off the bus, 800 times, for one answer

Mixture of experts

A router picks a handful.

8 of 256 read
far more parameters on disk — far fewer bytes per token

70 seconds. The grids do the work — just point.

"Here is the idea that broke the eight-point-nine-millisecond floor. In a dense model every parameter participates in every token, so decode is hostage to the total size of the thing. In a mixture of experts, a small router picks a handful of experts per token, and only those get read out of memory. The model on the right can have ten times the parameters of the one on the left and still be cheaper to decode — because decode is a bandwidth problem, and you just cut the bandwidth bill."

Concrete: DeepSeek-class models are hundreds of billions of parameters with only tens of billions active per token. That ratio is most of why serving costs collapsed over the last two years.

The catch, if asked: every expert still has to be resident in HBM somewhere, so you need either a very large box or expert parallelism across many GPUs — llm-d's third path. You trade memory capacity for memory bandwidth.

And back up again

the forward pass does not output a token

128,256 numbers. One wins.

temperature · top-p · top-k reshape this. temperature 0 is argmax — and still not reproducible, because batching changes the order of the sums.

50 seconds.

"Eleven milliseconds of silicon produced this: one floating-point score for every entry in the vocabulary. A hundred and twenty-eight thousand numbers, to choose one. Temperature, top-p and top-k reshape the distribution, and then we draw. And the fun fact for anyone who has fought a flaky eval: temperature zero is not a seed. The batch composition changes the order floating-point reductions happen in, which occasionally flips an argmax."

and then it has to become text

Your logo is a buffering problem.

60 seconds. This is the one built for this room. Enjoy it.

"I checked something this week specifically for you. Your logo is a die. One character, four bytes of UTF-8 — and the tokenizer splits it across two tokens, neither of which is a legal string on its own. So the server generates a token at step four hundred and twelve and physically cannot show it to you. It has to wait nine milliseconds for the next forward pass before those bytes become a character. Your conference logo is a buffering problem."

Then the serious half: inter-token latency is measured at token emission; your users experience character emission. For Cyrillic, for emoji, for CJK, those are different events — so a latency SLO built on token timestamps measures something nobody can feel.

Verified with tiktoken, o200k_base, decode_single_token_bytes. Say that — the room will assume it is a joke otherwise.

stop 08 · and round again

It was a tool call. Go again.

One user question is often five round trips — each one longer than the last. This is why prefix caching is not a nicety.

65 seconds. Closes the loop you opened on slide 3.

"And here is the part that surprises people who have only ever built chatbots. The answer that came back was not prose — it was a tool call. So your harness runs the tool, appends the result, and sends the entire conversation again. One question from a human is routinely five of these round trips, and every one is longer than the last. Your agent's cost does not grow linearly with the conversation. It grows with the square of it."

That is the business case for everything in act four: prefix caching, cache-aware routing, KV tiering. Without them an agent gets quadratically more expensive the better it works.

You are not renting intelligence.

"Eight stops. One request. And everything surprising was in the same place: the expensive state lives on the GPU — so routing, caching and batching turn out to be three names for one problem, which is keeping that state close to the request that needs it. Three things to leave them with if there is a lull: count your context before you buy a GPU; replace the Service with an InferencePool; and TTFT is compute while inter-token latency is bandwidth, so never reach for the same knob twice.

Likely questions: cost of a box (pivot to utilisation — the same card is cheap or ruinous depending only on how busy you keep it); MoE (lower per-token traffic, same shape); "do I need this for a 7B model" (no — but fix the routing the moment you have two replicas); frontier API vs self-host (a per-workload decision, not a per-company one); "is greedy decoding deterministic" (no, batch composition changes reduction order).
